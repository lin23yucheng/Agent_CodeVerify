# 提测前静态代码审查

## 目标

根据 CSV 中每条测试用例，审查配置的 Git 仓库和分支，判断开发代码是否实现了用例描述的功能和业务规则。审查仅基于源代码静态分析，不启动服务、不调用接口、不执行测试用例或代码。

## 执行步骤

1. 读取 `config/review-config.json`。使用配置的仓库地址和分支，或使用用户在本次对话中明确指定的仓库、分支或提交。
2. 将代码检出到临时工作目录，并记录实际审查的提交 SHA。不要把目标仓库克隆到本项目目录中。
3. 定位 `testcase_glob` 匹配的 CSV 文件。若匹配多个文件，逐个处理。保留原始 CSV，不覆盖输入文件。
4. 逐行阅读用例的所属模块、用例名称、前置条件、步骤和预期结果。结合代码入口、调用链、条件分支、数据校验、持久化和错误处理进行判断。需要时跨文件追踪实现，不以关键词命中作为实现证据。
5. 将审查结果写入 `results/` 下的对应 CSV 副本，在末尾追加 `result_column` 指定的列。保持原有列、行顺序和用例内容不变。
6. 完成后汇报结果文件路径、仓库分支、提交 SHA，以及已实现、未实现、不符合预期和无法判断的数量。

## 结论格式

每个用例单元格使用以下状态之一，并用简短文字说明判断依据。能够定位时附上相对文件路径和行号。

- `已实现`：代码逻辑覆盖预期行为，说明对应实现路径和关键条件。
- `未实现`：在相关入口和调用路径中未发现预期功能，说明检查过的代码位置。
- `实现不符合用例`：代码存在相关功能，但条件、边界、结果或异常处理与用例预期不一致，说明具体差异。
- `静态无法判断`：判断依赖运行时配置、外部服务、动态数据或仓库未提供的信息，说明缺少的证据。

## 单条用例判定原则

- 每条用例独立对照代码判定，不用其他用例的结论替代当前用例结论，也不因用例之间的预期存在矛盾而停止审查或调整结论。
- 以当前用例标题和预期结果表达的检查目标为主要判定依据，结合前置条件和步骤理解场景。若标题、步骤样例或预期之间有不一致，不自行改写用例意图。
- 对长度、必填、范围、格式等边界校验，直接检查代码中的实际限制规则，并与标题和预期表达的规则比较。步骤里的样例值用于辅助理解，若样例长度或取值与标题边界不一致，不让样例值覆盖标题表达的检查目标。可在结论说明中简短提示样例不一致，但仍按代码规则对照该条用例的标题和预期给出实现状态。
- 没有找到校验代码时，不推断校验存在。

## 输出要求

- 仅依据当前检出的代码和 CSV 内容，不臆测需求或运行结果。
- 将静态代码证据与运行时验证区分开。不得把静态审查表述为测试通过。
- 用例与代码无法建立关联时，标记 `静态无法判断` 并说明原因。
- CSV 使用标准 CSV 解析和写入方式，正确处理引号、逗号和单元格内换行，保留原文件编码；若无法确认编码或解析失败，停止写回并报告问题。
- 输出文件名使用原文件名加 `result_suffix`，放在 `results_dir` 中。
- 不修改开发仓库，不修改原始用例 CSV，不输出仓库凭据或密钥。
